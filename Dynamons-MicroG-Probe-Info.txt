New in 0.3.4 - official login activity and nested-launch ABI:
Pinned microG preferences_accounts.xml opens org.microg.gms.auth.login.LoginActivity
DIRECTLY. No account-manager ADD_REQUEST is expected before that activity opens;
the previous inference from missing account-request stages was insufficient.
Android 16 retains ten-argument IActivityManager.startActivity and also exposes an
eleven-argument feature/task-manager layout. The container's decoder assumed the
eleven-argument layout by OS version even for ten-argument calls. The nested launcher
also caught errors and returned success, and the caller discarded its result.
- Decodes launch arguments from the actual Intent position, supporting both valid layouts.
- Selects modern or legacy launch method signatures, inserting a feature slot only when declared.
- Preserves actual launch result codes; missing targets/errors no longer become success.
- Adds Open microG Google login to the host probe. Opens the SAME official LoginActivity
  as the upstream preference, through an explicit new-task container launch.
- Does not collect credentials, modify the microG APK or add email/token Intent extras.
- Logs LOGIN_ACTIVITY_CREATED only after the official activity's onCreate completed.
- Four ABI/status/error scenarios and five dual-layout/invalid-argument scenarios passed.
Phone test for this update: update existing probe, tap Open microG Google login.
If microG's sign-in introduction appears, continue using its Sign in button.
No runtime reinstall or download is required while prior verified files remain present.
Actual browser login/account creation/game profile persistence remain unverified.

Retained 0.3.3 - reviewed settings/account flow:
- Authenticator discovery enumerates installed services in the requested container
  user, even when no accounts exist. Refreshes on discovery and before binding.
- Rebuilds the complete authenticator catalog across actual container users instead
  of querying USER_ALL as though it were an installed profile. Installing an unrelated
  package no longer clears all other authenticator registrations. Publishes snapshots.
- Implements previously empty addAccountAsUser by forwarding to normal addAccount.
- Pending authenticator requests time out after 60 seconds if no result/login Intent
  arrives. A returned login Intent cancels this timer so user interaction is not timed out.
- Binding rejection returns an account-manager error; pending service connections
  are unbound on timeout/closure even if onServiceConnected never arrived.
- Provider registration selects the supported six-parameter installProvider overload.
  A failed mandatory microG settings provider raises a real error rather than being ignored.
- Stage-only diagnostics cover cache/discovery, account request, bind, service connection,
  login Intent/result/error/timeout and mandatory provider registration. Kept in a separate
  report section so later game launches do not hide the prior account-flow stages.
  No stage record contains account names, passwords, tokens or response Bundle contents.
- Five installed-authenticator selection scenarios and three provider registration
  contract checks passed, in addition to the previous validations.
These are confirmed source-level defects and bounded failure-handling changes. They
are not a guarantee against every future Google, network, SDK or publisher error.
Actual account creation, Google authentication, profile/save persistence and Arena
writes still require on-device testing. No server authentication check is bypassed.

Retained 0.3.2 provider fixes:
The user reached microG's splash then a blank screen; its SettingsContract.getSettings
threw IllegalArgumentException. The pinned upstream source uses require(cursor != null)
at that site. This is a null provider result, not proof of an account rejection.
- Replaced the provider wrapper's broad string rewrites with caller-slot-only handling.
  Provider URI, authority, projection, selection, sort order, method, args and Bundle
  payloads are preserved; Android AttributionSourceState uses the physical host UID.
- Provider exceptions are unwrapped and propagated instead of becoming null cursors,
  empty Bundles or fabricated success values.
- Android ContentProvider transport and AttributionSource validation use the real
  Binder caller UID; guest identities remain virtual outside those framework boundaries.
  Removed inherited stack-based conversion to privileged SYSTEM_UID.
- Settings launches stop only prior container microG processes, retaining runtime files,
  game data and account storage, to avoid reusing a stalled/frozen microG process.
- Six regression scenarios cover payload/reference preservation, exception propagation,
  real nullable results and the bounded physical/guest identity distinction.
These changes address observed provider handling problems. On-device settings and
Google login must be verified; no successful authentication is claimed.

Retained 0.3.1 launch fix:
Fixed a settings-launch defect: the explicit component Intent lacked Intent.package,
while the engine splash launcher required that package field and finished early.
The host now supplies the microG package, and the launcher also derives the package
from an explicit component when the package field is absent. Four regression cases
cover this path, normal game intents, package precedence and missing targets.
This updates the same com.dynamongamer.microgprobe host and retains its downloaded
runtime APKs/data. It does not require another 112 MB download or a new installation.
The game's supplied Cordova bridge uses legacy GoogleSignInClient (including silent
sign-in and getSignInIntent), plus Play Games PlayersClient for its player profile.
The pinned microG release declares sign-in and Games services; that declaration does
not prove successful account/profile authentication in this container.

Reason for this test:
The prior native-Google setup imported all required APKs, but the report showed a
Google service startup/provider-acquisition failure ending in SecurityException.
Source inspection found Google provider authorities forced to the phone provider
path, even when an imported provider existed. This probe routes those authorities
through guest-provider resolution and keeps OS settings/media/telephony on the OS path.
That fixes a concrete routing bug; it does not prove all Google login failures resolved.

Setup behavior:
- HTTPS downloads use only GitHub and its release asset hosts, with bounded redirects.
- Verifies exact sizes and hashes before any runtime import. Partial failures delete
  partial files and leave previous verified runtime files and container data intact.
- Validates guest package metadata and complete APK bytes after import.
- Opens exported org.microg.gms.ui.MainSettingsActivity explicitly; the selected
  official release has no default launchable activity.
- Original game's existing phone session/progress is not copied into this new host.
- Existing BlackBox and original/mod game applications are not uninstalled or updated.
- Repeated setup reuses verified files and imports; the guest game is stopped only
  before an actual runtime change, rather than on every setup click.

Identity and scope:
Removed the native-Google import UI, mock auth proxies inherited from prior source,
and fabricated Play Store PackageInfo in this host. Storage imports report their
actual APK certificate metadata instead of inheriting a same-named phone app signer.
Does not grant signature-spoofing or privileged OS permissions, forge account tokens,
copy outside accounts, override auth results, or bypass publisher/server verification.
A failed microG Self-Check is a compatibility failure to report, not proof of login.
Some clients require trusted Google signing certificates or features microG does not
implement; this probe does not promise those checks will pass or modify them.
No mod-menu attachment, save transfer, leaderboard-write success or login guarantee.
