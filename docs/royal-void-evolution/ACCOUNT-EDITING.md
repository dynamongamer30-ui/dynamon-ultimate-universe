# Account form reliability — phase 17 increment

This increment preserves Google sign-in, the existing profile insert/update paths, current-user profile RPC, account IDs, username uniqueness rules, role flags and award rules. It makes no database, policy, grant, notification or native-source changes. Synthetic account creation and edits are restricted to intercepted localhost traffic; no production account is created or edited for testing.

## Username checks

Onboarding and profile editing share `useUsernameAvailability`. Checks retain the existing 3–24 letter/number/underscore validation and 350 ms debounce. A result is associated with the current account, trimmed name and retry revision, so a previous name's successful response cannot enable the current form even before the next effect runs. Superseded reads are canceled and guarded against late settlement. A ten-second availability deadline and explicit failure/retry state prevent an unsuccessful check from being presented as available. Only boolean RPC results are accepted; no polling or automatic retries are introduced. An unchanged existing username needs no availability call. The server remains authoritative for uniqueness when saving.

## Drafts and writes

The profile editor is keyed to the signed-in account and starts with a snapshot of its loaded profile. Background profile refreshes update the shared account data without replacing the editor's draft. Confirmed saves trim the submitted name/username and retain that username as the editor's saved baseline, including if a subsequent shared refresh fails.

Both forms use a synchronous pending lock and disabled fieldset, including avatar/gender controls. A successful update/upsert must return the current user's ID before success feedback or onboarding continuation. Rejected writes and error-free empty responses retain the draft and show inline retry guidance. Late settlement after disposal does not update the form or show success. Existing authenticated SELECT permission on profile ID was verified with a read-only catalog query; no grant change is required. The live username RPC contract was also inspected read-only and retained unchanged.

Initial profile-load failure is distinct from a successfully loaded missing profile. A failed read offers Retry profile rather than opening setup or an editable fallback. After a confirmed missing-profile response, a background read failure shows retry feedback without unmounting an existing onboarding draft. The shared hook exposes whether a successful snapshot has been loaded to distinguish those states.

## Return navigation

After a confirmed onboarding write, the shared profile refresh feeds one auth-route redirect. It consumes the existing stored relative return path once. The effect is restricted to the active `/auth` route: the application's page transition can briefly remount the previous outlet during navigation, which otherwise consumes the hint again and replaces the requested destination with `/mods`. The existing validation of stored paths and default destination remain unchanged. General route-transition architecture is not rewritten.

The first onboarding baseline stopped at its five-second visibility assertion before initial client loading finished; it did not reproduce the race. A retained trace showed the client loading interval, and tests now use the same explicit site-settings-ready marker as other suites.
