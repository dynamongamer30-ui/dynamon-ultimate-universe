# Progression client reliability — 24 October 2026


## Phase 19 — confirmed daily check-in and progression account state (24 October 2026)

DailyCheckIn previously wrote a session marker before touch_streak returned, and never cleared that attempted flag after failure. GamificationProvider used whole-user object dependencies and unguarded asynchronous state updates, allowing old account reads/awards to replace current state. Initial reads could also overwrite a newly confirmed streak/XP response.

The provider now keeps an account scope token, cancels its requests on disposal, hides old-account values synchronously and clears state on sign-out. Progress reads and the existing record_engagement/touch_streak RPC paths have ten-second request deadlines and SDK retries disabled. Refresh generation and per-field mutation revisions prevent stale refreshes from replacing confirmed XP/streak responses. Late responses from a previous account cannot set current values or emit award toasts. The current server award parameters/amount rules are unchanged. Progress read errors have explicit lookup retry; compact badges distinguish loading/error, and the full streak card exposes check-in recovery.

Only a valid current-account streak result records streak-checkin:user:UTC-day=confirmed. Legacy value 1 meant attempted rather than proven completion, so it triggers one recheck rather than being trusted; a failed recheck leaves it unconfirmed. An incremented=false row still confirms the existing server result. One in-flight promise prevents duplicate check-in writes, and an in-memory confirmation also works when optional session storage is unavailable. Failed/null/stalled responses expose Retry daily check-in. A one-shot timer checks the next UTC day, then schedules the next boundary; this is not a short-interval polling loop. The repository RPC already uses UTC/same-day behavior. Timeouts can still mean a request committed server-side; retry relies on that existing server behavior and does not promise rollback. The card no longer tells users to come back tomorrow before confirmation, and singular-day copy is correct.

All 52 local browser checks pass in 3.9 minutes across Chrome phone/tablet/desktop and WebKit: ten progression cases, one three-route signed-out case and two existing account-cache cases per project. This includes failure/empty response, acknowledgment-only markers, legacy marker repair, repeated-click lock, stale read/mutation ordering, account switch, old award toast suppression, a stalled check-in, explicit read retry and UTC rollover. Four focused retry-layout repeats pass in 39.8 seconds at 320/1440 pixels with document fit and at least 44-pixel targets. The phone fixture was visually reviewed; a final phone repeat after copy refinement passes. TypeScript/final production build and all 31 existing Node tests pass, with zero lint errors and 12 existing Fast Refresh warnings. Generated sitemap output was restored.

Early UTC-fixture attempts failed first because the synthetic session expired relative to the advanced clock, then because startup crossed the boundary, then because pausing before hydration stalled initialization. The fixture now uses a longer-lived synthetic session, allows initialization at 23:50 UTC and fast-forwards the remaining interval after the first confirmed result. The dedicated corrected case and full 52-case run pass. These attempts are retained, not represented as runtime failures or hidden passing runs. Clock behavior was checked against [Playwright documentation](https://playwright.dev/docs/clock). Development tagger hydration warnings and the existing Firefox Windows launch limit remain recorded.

Production metadata-only verification confirms the existing authenticated-callable RPC signatures/return types, auth.uid references and touch_streak UTC reference. No real progression row or mutating RPC was used for QA, and no database definition/grant/policy changed. All synthetic-account Supabase traffic is intercepted and guards skip those cases outside localhost. Browser-tool availability remains unchanged from the reward lookup increment: no new authenticated live UI/mutation check can be claimed. Public rollout checks follow.

This increment does not certify notification reward claims, pass consumption, trainer-rank component account state, within-account concurrent award response ordering, server-side concurrency/locking, offline/real-device behavior or fresh OAuth. Those and the broader Phase 19/roadmap remain follow-up work; prior approved security fixes remain applied.
