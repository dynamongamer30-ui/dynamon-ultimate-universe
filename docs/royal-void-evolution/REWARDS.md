# Reward lookup reliability — 24 October 2026


## Phase 19 — read-only reward lookup reliability (24 October 2026)

The rewards page previously used a single mounted-page checked flag and unguarded local state. A failed lookup was silently treated as no result; retry was unavailable, another account could inherit the prior page state, and late responses could repopulate old reward data. The DailyKeyCard also retained a claim branch even though its only caller rendered already-claimed keys. That branch was unreachable from the normal page and contradicted the page's read-only intent.

The page now mounts an account-keyed reward region and uses independent, typed TanStack queries for my_daily_key and my_active_phoenix_pass. Each query cancels on disposal, has a ten-second request deadline, disables SDK/query retries and focus/reconnect refetch, and removes inactive cache immediately. Errors are explicit; retry requests only failed/missing-key information and preserves a successful reward from the other lookup. Current-account loading, an empty result and an uncollected-key Notifications notice are separate states. The lookup region never claims or consumes a reward. The unreachable claim code and stale loose-RPC wrapper were removed; notification claim paths, server contracts and permissions are unchanged.

Collected key display takes its current value from the result, wraps long values inside the layout and reports clipboard failure with a manual-selection fallback. Clipboard feedback/timers stop after card disposal; the OS clipboard action itself is not claimed cancelable. Local tests stub clipboard writes completely and use visibly synthetic FIXTURE-ONLY keys. No real keys are printed/exported or copied for QA. The unconditional Works for 24 hours copy was removed from the collected-key display because the client lookup does not establish remaining license duration.

Validation: all eight focused desktop cases pass in 1.1 minutes, followed by all 36 local browser checks (eight account reward cases and one signed-out case per Chrome phone/tablet/desktop/WebKit project) in 3.2 minutes. Cases cover source-specific partial failure/retry, missing claimed-key value, held-request timeout, account switch while loading, late result after sign-out, uncollected-key guidance, clipboard failure/success and long-key widths 320/600/1440. The account-switch signal is synthetic SDK broadcast, not real OAuth. All Supabase traffic is intercepted and these fixtures skip outside localhost. TypeScript/build and all 31 Node tests pass; lint remains zero errors/12 existing Fast Refresh warnings. Build-generated sitemap output was restored. The long-key desktop fixture screenshot was visually reviewed. Development tagger hydration warnings and the existing Firefox runtime limitation remain recorded, not clean passing gates.

A metadata-only production check confirms both lookup functions have no arguments, match generated return types, use SQL, are executable by authenticated and reference auth.uid(); their bodies contain no write-operation keyword. This supplements the repository definitions and is not a full function dependency/security audit. No RPC was executed against real reward rows during that check. No new database schema, role, grant, policy or draw behavior is introduced.

Authenticated live validation is unavailable this increment: the prior mcp__cua_repl namespace was removed mid-turn, and the catalog-listed control-in-app-browser SKILL.md is absent from the indicated cache path and searched skill roots.
