# Achievement catalog and earned-badge states — 24–25 October 2026

The achievements page previously treated a failed catalog as an empty list, used earned keys without knowing whether their lookup succeeded, and displayed a default unlocked/level/streak footer. A failed private lookup could therefore make unknown badges appear unearned, while a catalog failure could produce a misleading denominator. A confirmed engagement award could also leave an older badge snapshot looking current.

## Catalog and ownership

The badge collection now uses a shared typed catalog query with explicit loading, error/retry and confirmed-empty states. It selects the displayed fields, orders by XP then key, validates row shape/nonnegative integral XP and rejects duplicate keys. Requests are cancellable, bounded to ten seconds and have SDK/query retries disabled. The public catalog is fresh for 60 seconds across mounts, with no focus/reconnect refetch or polling. The collection mounts only for a signed-in account on the achievements route; signed-out visitors no longer fetch an unused catalog.

Earned ownership reuses the existing GamificationProvider lookup. No second automatic private badge query is added. The provider now exposes a scoped achievement status separately from its existing aggregate progress error flag. A successful earned-key array is validated and deduplicated; null/malformed/failed data is not treated as confirmed zero. A healthy earned result can be displayed even if another progress source failed. Loading/error/stale snapshots do not publish Earned/Not earned labels, lock/grayscale treatment or totals. Cards instead state Checking, Status unavailable or Refresh needed. A successful empty array is the state that permits confirmed unearned labels.

The rollup counts keys matched to the displayed catalog, so obsolete or duplicate earned keys cannot inflate it. An empty/unavailable catalog has no fabricated zero denominator. The duplicated level/streak footer was removed; their existing dedicated cards retain their own status UI. Catalog retry fetches only the public catalog. Earned retry uses the existing shared progress refresh, including its XP/streak/earned reads and account/request guards; it is not a claim or award operation.

## Confirmed awards and stale responses

A valid `record_engagement` response with `awarded: true` marks the badge snapshot stale and advances an achievement revision. An older in-flight progress lookup cannot replace that state with old keys or declare the snapshot current. The badge page offers an explicit Refresh earned badges action. That refresh must succeed before the ownership labels/count return. Failed refresh preserves unknown status rather than displaying previously cached ownership as current. No automatic post-award fetch loop or extra engagement call is introduced. This does not certify cross-device synchronization or broader within-account XP response ordering.

Account change/sign-out continues to use the provider's scope guard and immediate value hiding. The collection is also account-keyed. Public catalog data may be shared; private ownership is never inferred from the previous account. Badge status text, wrapping content and a 44-pixel retry target make recovery usable at narrow widths. Existing tier appearance is retained with a safe fallback for unknown tiers; background opacity now uses explicit classes rather than a constructed class token.
